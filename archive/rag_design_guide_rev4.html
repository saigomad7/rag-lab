① Gemini 안 검토 결과

판정 기준: 채택 그대로 사용 · 보완 방향은 맞고 추가 필요 · 수정 이대로면 문제 발생 · 누락 빠진 설계

결론: Gemini 안의 뼈대(BGE-M3 dense+sparse, Milvus 하이브리드, 리랭커, 헤더 부착, 공통+JSON 메타)는 받아들이고, 권한 · 날짜 · 동기화 · 청크/로그 테이블 · 질의 분석을 더한 것이 아래 권장 설계입니다.
Re-review

①-2 재검토에서 달라진 점 (rev2)

처음 질문으로 돌아가 rev1의 답을 다시 봤습니다. 방향은 유지하되, 실제로 진행하면 걸리게 될 8곳을 고쳤습니다.

순서

R1 · 평가 인프라보다 스모크 테스트가 먼저

rev1은 로그 테이블 · 골든셋 100문항부터 만들라고 했는데, 그것만 2~3주입니다. 실제 질문 20개를 지금 시스템에 넣고 실패 유형을 분류하면 반나절에 병목이 보입니다. Quick Win 순서를 추측(청킹→메타→BM25)이 아니라 이 분포로 정합니다.

함정

R2 · 골든셋 정답을 청크 ID로 묶으면 안 됨

Phase 3에서 재청킹하는 순간 청크 ID가 전부 바뀌어 골든셋이 무효가 됩니다. 정답은 문서 ID + 정답 문장(텍스트)으로 기록하고, 평가 때 텍스트 겹침으로 청크 적중을 판정합니다.

설계

R3 · 헤더는 dense에만, sparse는 본문만

헤더를 sparse 벡터에도 넣으면 같은 문서의 모든 청크가 기관명 · 날짜 토큰으로 매칭되어 키워드 검색이 문서 단위로 뭉개집니다. BGE-M3는 한 번의 인코딩으로 둘 다 나오므로 입력 텍스트를 두 벌(dense=헤더+본문, sparse=본문)로 넣어 비교합니다.

옵션

R4 · Oracle Text 한국어 형태소 인덱스

청크가 이미 Oracle에 있으므로 KOREAN_MORPH_LEXER로 텍스트 인덱스를 걸면 새 인프라 없이 형태소 기반 키워드 검색이 됩니다. D1의 비교 대상에 추가(Kiwi BM25 · BGE sparse · Oracle Text 3자 비교).

누락

R5 · 성능 예산과 용량을 먼저 정한다

응답 시간 목표(p95)가 없으면 리랭커 크기 · 후보 수 · LLM 문맥 생성 여부를 고를 기준이 없습니다. v2 컬렉션 병행은 저장소 2배 + 전체 재임베딩 시간이 드니 Phase 0에서 산정합니다.

누락

R6 · 검색 결과의 근사 중복 접기

적재 때 중복을 지워도 뉴스 재송고 · 메일 인용은 남습니다. 리랭크 뒤 문서당 최대 N개 + 텍스트 유사도 높은 청크 접기를 넣어야 상위 5개가 같은 내용으로 차지 않습니다.

단순화

R7 · 골든셋은 자라게 둔다

100문항을 완성하고 시작하지 않습니다. 스모크 20 → 합성 50 → 로그 · 피드백에서 계속 추가. 버전만 고정하면 됩니다.

운영

R8 · 추적은 한 곳에서 (rev3에서 갱신)

진행 추적은 단계별 체크리스트(rag_stage_checklist_rev2, S01~S21)에서 합니다. 퀘스트 보드 rev3는 항목별 옵션 · 완료 조건의 상세 사전, 이 문서는 설계 원본입니다. 체크 상태를 여러 문서에 나눠 갖지 않습니다.

정의

Phase를 두 개로 다시 나눔

Phase 1 = RAG 평가 · 개선(이 문서의 ②~⑦). Phase 2 = 마켓 센싱(⑧): 사내 관점의 축을 정의하고 축별로 외부 이상을 감지. Phase 1을 시작하기 전에 Phase 2 적합성 검토를 병행합니다.

추적

진행은 파이프라인 단계 기준으로

시간 순서(Phase 0~5)가 아니라 데이터 · 질의가 흐르는 순서로 확인합니다. 적재 S01~S06, 검색 S07~S14, 평가 S15, 센싱 S16~S21. 단계마다 체크 항목 · 현 수준(기입) · 개선 아이템 · 우선순위를 한 표로 봅니다(rag_stage_checklist_rev2).

검색

MMR을 RRF와 함께

RRF는 BM25 · dense · sparse 목록을 합치는 자리, MMR은 리랭크 뒤에 비슷한 청크를 밀어내는 자리입니다. 대체 관계가 아니므로 둘 다 넣습니다(λ 0.5~0.7 실험). 센싱에서는 재송고 뉴스 때문에 MMR이 더 중요합니다.

Decisions

③ 핵심 설계 결정

D1

키워드 검색: BGE-M3 sparse vs 형태소 BM25

BGE-M3 sparse는 서브워드 기반이라 조사 문제는 덜하지만, 제품 코드명 · 숫자 · 희귀 고유명사 매칭은 BM25가 나을 수 있습니다. 기본은 Dense + Sparse, 골든셋으로 +BM25(Kiwi) 3-way를 비교해 이득이 있을 때만 BM25 유지. Milvus 2.5 이상이면 BM25도 Milvus 안에서 처리 가능. 청크가 이미 Oracle에 있으니 Oracle Text(KOREAN_MORPH_LEXER)도 인프라 추가 없는 후보로 함께 비교.

D2

필터는 Milvus에서, 원장은 Oracle에서

검색할 때 필터(유형 · 날짜 · 권한)는 Milvus 스칼라 필드로 걸어야 벡터 검색과 동시에 적용됩니다. Oracle에서 거르고 ID를 넘기는 방식은 느리고 결과가 빠집니다. Oracle은 원본 · 이력 · 동기화의 기준(Source of Truth)입니다.

D3

공통 컬럼 vs META_EXTRA 승격 기준

필터 · 권한 · 정렬 · 인용에 쓰면 공통 컬럼(양쪽 DB에 모두), 화면 표시나 참고용이면 JSON. 예: security_level, 기관명, 작성일은 공통 / reporter, opinion, thread_id는 JSON.

D4

청크 본문을 Milvus에도 저장

리랭커가 본문을 바로 읽어야 하므로 Milvus에 텍스트를 함께 두면 Oracle 왕복이 사라집니다. 원본 기준은 Oracle이고, Milvus 본문은 사본입니다.

D5

질의 분해는 "필요할 때만"

모든 질문을 분해하면 고유명사 누락 · 지연이 생깁니다. 질의 분석 단계는 항상(기간 · 유형 · 엔티티 → 필터), 분해는 비교 · 종합형 질문에만, 원 질의 검색은 항상 포함.

D6

버전을 모든 층에 남긴다

파서 · 청커 · 헤더 템플릿 · 임베딩 설정이 바뀌면 결과가 달라집니다. CHUNKER_VER, EMBED_VER를 저장하고, 새 버전은 새 컬렉션(rag_chunks_v2)에 적재해 골든셋으로 비교한 뒤 전환(alias 교체)합니다.

Oracle Meta DB

④ Oracle 스키마 (권장)

기존 원문 · 청크 테이블은 버리지 않습니다. RAG_DOC을 두고 원천 키(SRC_SYSTEM + SRC_KEY)로 기존 원문 테이블과 연결하고, 기존 청크 테이블은 아래 RAG_CHUNK 컬럼 기준으로 확장합니다.

원장

RAG_DOC

문서 1건 = 1행. 공통 메타 · 보안등급 · 태그 · 가변 메타(JSON) · 해시 · 삭제 플래그

권한

RAG_DOC_ACL

문서별 열람 가능 그룹 · 사용자. 메일 수신자, 임원 보고서 결재선 등

DDL — 핵심 4개 테이블 (Oracle 19c 기준)

-- 1) 문서 원장: 필터·권한·정렬·인용에 쓰는 값은 공통 컬럼, 나머지는 META_EXTRA
CREATE TABLE RAG_DOC (
  DOC_ID          VARCHAR2(64)        PRIMARY KEY,
  SRC_SYSTEM      VARCHAR2(32)        NOT NULL,   -- 원천 시스템: NEWS_CRAWL, BROKER_FEED, MAIL, KMS ...
  SRC_KEY         VARCHAR2(200)       NOT NULL,   -- 기존 원문 테이블의 키
  DATA_SOURCE     VARCHAR2(16)        NOT NULL CHECK (DATA_SOURCE IN ('INTERNAL','EXTERNAL')),
  DOC_TYPE        VARCHAR2(32)        NOT NULL,   -- 9종 코드 (아래 표)
  TITLE           VARCHAR2(1000 CHAR),
  PUBLISHED_AT    DATE,                           -- 작성·발행일. 모르면 NULL (SYSDATE 기본값 금지)
  DATE_QUALITY    VARCHAR2(10) DEFAULT 'EXACT' NOT NULL,  -- EXACT / ESTIMATED / MISSING
  ORG_NAME        VARCHAR2(200 CHAR),             -- 언론사·증권사·기관·작성 부서
  AUTHOR          VARCHAR2(200 CHAR),
  SRC_URL         VARCHAR2(2000),                 -- 원문 링크 (답변 인용용)
  LANG            VARCHAR2(8)  DEFAULT 'ko' NOT NULL,
  SECURITY_LEVEL  NUMBER(1)    NOT NULL,          -- 0 공개(사외) 1 사내일반 2 대외비 3 임원
  TAGS            CLOB CHECK (TAGS IS JSON),      -- {"company":[..],"product":[..],"topic":[..]} 센싱 대비
  META_EXTRA      CLOB CHECK (META_EXTRA IS JSON),
  CONTENT_HASH    VARCHAR2(64),                   -- 본문 SHA-256: 중복·변경 감지
  IS_DELETED      CHAR(1)      DEFAULT 'N' NOT NULL,
  REG_DATE        DATE         DEFAULT SYSDATE NOT NULL,
  UPD_DATE        DATE         DEFAULT SYSDATE NOT NULL,
  CONSTRAINT UQ_RAG_DOC_SRC UNIQUE (SRC_SYSTEM, SRC_KEY)
);
CREATE INDEX IX_RAG_DOC_TYPE_DT ON RAG_DOC (DOC_TYPE, PUBLISHED_AT);
CREATE INDEX IX_RAG_DOC_UPD     ON RAG_DOC (UPD_DATE);       -- 증분 동기화용
CREATE INDEX IX_RAG_DOC_HASH    ON RAG_DOC (CONTENT_HASH);   -- 중복 탐지용

-- 2) 권한: 그룹/사용자 단위. 사외 문서는 ('ALL','*') 한 줄
CREATE TABLE RAG_DOC_ACL (
  DOC_ID          VARCHAR2(64)  NOT NULL REFERENCES RAG_DOC (DOC_ID),
  PRINCIPAL_TYPE  VARCHAR2(8)   NOT NULL,         -- ALL / GROUP / USER
  PRINCIPAL_ID    VARCHAR2(100) NOT NULL,
  CONSTRAINT PK_RAG_DOC_ACL PRIMARY KEY (DOC_ID, PRINCIPAL_TYPE, PRINCIPAL_ID)
);

-- 3) 청크: 헤더는 본문과 분리 보관 → 템플릿이 바뀌면 재임베딩만
CREATE TABLE RAG_CHUNK (
  CHUNK_ID        VARCHAR2(100) PRIMARY KEY,      -- DOC_ID || '_' || LPAD(CHUNK_SEQ,4,'0')
  DOC_ID          VARCHAR2(64)  NOT NULL REFERENCES RAG_DOC (DOC_ID),
  CHUNK_SEQ       NUMBER(6)     NOT NULL,
  PARENT_ID       VARCHAR2(100),                  -- Parent-Child 구조용
  CHUNK_KIND      VARCHAR2(10)  DEFAULT 'TEXT' NOT NULL,  -- TEXT / TABLE / SUMMARY
  SECTION_PATH    VARCHAR2(1000 CHAR),            -- 예: 2. 수요 전망 > 2.1 HBM
  HEADER_TEXT     VARCHAR2(1000 CHAR),            -- [유형 | 날짜 | 기관 | 제목 | 섹션]
  CHUNK_TEXT      CLOB          NOT NULL,
  TOKEN_CNT       NUMBER(6),
  CHUNKER_VER     VARCHAR2(16)  NOT NULL,
  CONTENT_HASH    VARCHAR2(64),
  IS_DELETED      CHAR(1)       DEFAULT 'N' NOT NULL,
  UPD_DATE        DATE          DEFAULT SYSDATE NOT NULL
);
CREATE INDEX IX_RAG_CHUNK_DOC ON RAG_CHUNK (DOC_ID, CHUNK_SEQ);

-- 4) 벡터 동기화 상태: Oracle ↔ Milvus 정합성의 기준
CREATE TABLE RAG_VEC_SYNC (
  CHUNK_ID        VARCHAR2(100) NOT NULL,
  COLLECTION      VARCHAR2(64)  NOT NULL,         -- rag_chunks_v1 ...
  EMBED_MODEL     VARCHAR2(64)  NOT NULL,         -- bge-m3
  EMBED_VER       VARCHAR2(16)  NOT NULL,         -- 헤더 템플릿·max_length 등 설정 버전
  STATUS          VARCHAR2(10)  NOT NULL,         -- PENDING / DONE / ERROR / DELETED
  SYNCED_AT       DATE,
  ERR_MSG         VARCHAR2(1000 CHAR),
  CONSTRAINT PK_RAG_VEC_SYNC PRIMARY KEY (CHUNK_ID, COLLECTION)
);
Oracle 버전별 JSON 저장: 19c는 CLOB + IS JSON으로 충분하고, 21c 이상이면 네이티브 JSON 타입이 더 빠릅니다. JSON 안의 키로 자주 조회한다면 JSON_VALUE 함수 기반 인덱스를 추가하세요. 로그 · 평가 테이블 DDL은 골든셋 퀘스트(Q06~Q08) 때 확정합니다.

Milvus

⑤ Milvus 컬렉션 스키마 (권장)

검색 시점에 필터로 쓰는 값은 모두 스칼라 필드로 복제합니다. Oracle의 RAG_DOC · RAG_CHUNK에서 필요한 컬럼만 가져오고, 본문은 리랭커용 사본으로 둡니다.

인덱스 · 검색 설정

Dense

HNSW · metric IP (정규화 후) 또는 COSINE

  • M 16~32, efConstruction 200~256
  • 검색 ef 128부터 시작, 골든셋으로 지연–재현율 곡선 확인
  • FLAT 인덱스로 같은 골든셋을 돌려 ANN 손실이 있는지 1회 점검
Sparse

SPARSE_INVERTED_INDEX · metric IP

  • BGE-M3 sparse 출력은 lexical weight이므로 IP
  • drop_ratio_search는 0으로 시작(전부 사용)
하이브리드

hybrid_search + RRFRanker(k=60)

  • 각 검색기 limit 50, 리랭커 후보 50
  • 가중합(WeightedRanker)은 점수 분포가 질의마다 달라 불안정 — 측정 후에만 채택
  • 필터 표현식은 두 검색기에 동일하게 적용
운영

컬렉션 버전 + alias

  • rag_chunks_v1, rag_chunks_v2 … 실제 이름
  • 서비스는 alias rag_chunks만 바라봄 → 검증 후 alias 교체로 무중단 전환
  • 파티션은 data_source 기준 2개 정도면 충분, 과하게 쪼개지 않음
# 필터 표현식 예 — 서버가 사용자 그룹으로 조립 (클라이언트 입력 금지)
expr = (
  "security_level <= {lvl} "
  "and array_contains_any(acl, {groups}) "
  "and published_at >= {from_day} "          # 질의 분석에서 추출한 기간
  "and doc_type in {types}"                   # 없으면 절 제거
)
res = client.hybrid_search(
  collection_name="rag_chunks",            # alias
  reqs=[AnnSearchRequest(dense_vec,  "dense",  {"ef": 128}, limit=50, expr=expr),
        AnnSearchRequest(sparse_vec, "sparse", {}, limit=50, expr=expr)],
  ranker=RRFRanker(60), limit=50,
  output_fields=["chunk_id","doc_id","doc_type","org_name","published_at","header_text","chunk_text"])

버그

조회 SQL — 실행 불가

FROM 절이 없고 JSON 경로가 ' .security_level'로 깨져 있습니다. 또 보안등급은 공통 컬럼으로 승격했으므로 JSON을 뒤질 이유가 없습니다.

-- 수정 (공통 컬럼 사용)
SELECT DOC_ID, TITLE FROM RAG_DOC
 WHERE SECURITY_LEVEL >= 2 AND IS_DELETED = 'N';

-- JSON 안의 값을 조회할 때의 올바른 형태
SELECT DOC_ID FROM RAG_DOC
 WHERE JSON_VALUE(META_EXTRA, '$.opinion') = 'BUY';
버그

INSERT → MERGE (재실행 안전)

같은 스크립트를 두 번 돌리면 PK 충돌로 멈춥니다. 원천 키 기준 MERGE로 바꾸면 신규는 삽입, 변경은 갱신됩니다.

MERGE INTO RAG_DOC d
USING (SELECT :1 SRC_SYSTEM, :2 SRC_KEY FROM dual) s
   ON (d.SRC_SYSTEM = s.SRC_SYSTEM AND d.SRC_KEY = s.SRC_KEY)
WHEN MATCHED THEN UPDATE SET
     TITLE=:3, PUBLISHED_AT=:4, META_EXTRA=:5,
     CONTENT_HASH=:6, UPD_DATE=SYSDATE
WHEN NOT MATCHED THEN INSERT (DOC_ID, SRC_SYSTEM, SRC_KEY, DATA_SOURCE,
     DOC_TYPE, TITLE, PUBLISHED_AT, SECURITY_LEVEL, META_EXTRA, CONTENT_HASH)
  VALUES (:7, :1, :2, :8, :9, :3, :4, :10, :5, :6);
주의

CLOB 바인딩 · 날짜 · 계정

  • JSON이 4000바이트를 넘으면 cursor.setinputsizes(META_EXTRA=oracledb.DB_TYPE_CLOB) 지정
  • CREATED_AT은 pandas Timestamp가 아니라 datetime으로 변환해 바인딩, 모르면 None
  • 접속 정보는 코드에 쓰지 않고 환경변수 · 사내 비밀 저장소에서 읽기
  • executemany에 batcherrors=True로 일부 실패 시 원인 행 확인
보완

메일 수신자는 JSON이 아니라 ACL 행으로

Gemini 샘플의 recipients 배열은 표시용으로만 JSON에 두고, 권한 판단에 쓰려면 RAG_DOC_ACL에 (DOC_ID, 'USER', 사번) 행으로 풀어 넣어야 Milvus acl 배열로 옮길 수 있습니다.

Phase 2

⑧ 마켓 센싱 설계 — RAG 로직 중 무엇을 그대로 쓰고 무엇을 바꾸는가

RAG는 질문이 들어와야 움직이는 pull이고, 센싱은 주기적으로 스스로 도는 push입니다. 부품은 거의 다 재사용되지만 흐름의 앞뒤가 바뀝니다.

센싱 흐름과 Phase 1 부품의 재사용

노란 상자가 RAG와 달라지는 자리입니다. 질의 분해 → 축별로 한 번 설계해 두는 상시 질의, 답변 생성 → 이전 창 대비 변화 비교. 점선은 Phase 1에서 그대로 올라오는 부품입니다.

-- 축 · 하위 신호별 상시 질의. 한 번 설계하면 버전으로 관리
CREATE TABLE SENSE_WATCH_QUERY (
  WQ_ID        VARCHAR2(32)  PRIMARY KEY,
  AXIS         VARCHAR2(32)  NOT NULL,   -- DEMAND / SUPPLY / PRICE / TECH / POLICY / CUSTOMER
  SIGNAL       VARCHAR2(64)  NOT NULL,   -- 예: PRICE.DRAM_CONTRACT
  QUERY_TEXT   VARCHAR2(1000 CHAR) NOT NULL,
  FILTER_EXPR  VARCHAR2(1000 CHAR),      -- doc_type · tags 필터 템플릿 (기간 창은 실행 시 주입)
  WINDOW_DAYS  NUMBER(3)     DEFAULT 7,  -- 이번 창
  BASE_WEEKS   NUMBER(2)     DEFAULT 4,  -- 기준선 창
  VER          VARCHAR2(16)  NOT NULL,
  IS_ACTIVE    CHAR(1)       DEFAULT 'Y'
);
-- 실행 1회 = 창 1개 × 질의 1개. 이전 창과의 비교가 여기서 나옴
CREATE TABLE SENSE_RUN (
  RUN_ID       VARCHAR2(40)  PRIMARY KEY,
  WQ_ID        VARCHAR2(32)  NOT NULL REFERENCES SENSE_WATCH_QUERY,
  WIN_FROM     DATE NOT NULL,  WIN_TO DATE NOT NULL,
  HIT_CNT      NUMBER(6),      -- 중복 접은 뒤 사건 수
  BASE_AVG     NUMBER(8,2),    -- 기준선 평균
  SCORE        NUMBER(6,3),    -- 이상 점수
  ALERTED      CHAR(1) DEFAULT 'N',
  RAN_AT       DATE DEFAULT SYSDATE
);
CREATE TABLE SENSE_HIT (          -- 실행별 근거 문서 (요약 인용 · 피드백 대상)
  RUN_ID VARCHAR2(40) NOT NULL, DOC_ID VARCHAR2(64) NOT NULL, CLUSTER_ID VARCHAR2(40),
  RERANK_SCORE NUMBER(6,4), DIRECTION VARCHAR2(16), IS_NEW_ENTITY CHAR(1),
  PRIMARY KEY (RUN_ID, DOC_ID)
);
CREATE TABLE SENSE_EVENT (        -- 백테스트용 과거 실제 사건 (센싱의 골든셋)
  EVENT_ID VARCHAR2(32) PRIMARY KEY, AXIS VARCHAR2(32), SIGNAL VARCHAR2(64),
  EVENT_DATE DATE NOT NULL, TITLE VARCHAR2(500 CHAR), EVIDENCE_DOC_IDS CLOB
);

신호 2

새 엔티티

이전 창에 없던 회사 · 제품 · 지역 태그의 수. TAGS가 있어야 가능(S05-5).

신호 3

방향 변화

사내 LLM이 사건마다 방향 라벨(증설/감산, 상승/하락)을 붙이고 창 간 분포 변화를 봄. 비용이 있어 백테스트에서 이득이 있을 때만.

score = w₁·z(언급량) + w₂·새 엔티티 수 + w₃·방향 변화 — 가중치와 임계는 정하지 않고 시작합니다. SENSE_EVENT의 과거 사건 10건 이상을 과거 창으로 돌려 회수율이 높고 오탐이 낮은 조합을 고르고, 운영 중에는 담당자의 유효 · 무효 표시로 조정합니다.
